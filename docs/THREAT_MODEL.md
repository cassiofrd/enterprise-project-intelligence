
# Threat Model — Enterprise Project Intelligence

**Project:** Enterprise Project Intelligence  
**Environment:** Microsoft Foundry, Python, GitHub Actions  
**Last reviewed:** 2026-11-04  
**Scope:** Educational AI agent security laboratory

## 1. Overview

Enterprise Project Intelligence is an experimental AI application
that retrieves synthetic project information and calculates
financial performance indicators.

The application combines a Microsoft Foundry agent, Python
function calling, authorization checks, tool validation,
and deterministic financial output validation.

This document describes the main security threats,
implemented controls, and remaining risks.

The laboratory is not a production-certified security solution.

## 2. Assets to Protect

| Asset | Security objective |
|---|---|
| Project information | Prevent unauthorized access and modification |
| Financial indicators | Preserve calculation and output integrity |
| Tool execution | Prevent unauthorized or excessive execution |
| Agent instructions | Prevent untrusted data from overriding trusted rules |
| Credentials | Prevent accidental disclosure |
| Execution logs | Minimize exposure of sensitive information |
| Source code | Monitor dependencies and accidental secret publication |

All project records used in this laboratory are synthetic.

## 3. Architecture and Trust Boundaries

The application includes:

1. User requests.
2. A Microsoft Foundry agent that selects tools.
3. Python functions that authorize and execute tool calls.
4. Synthetic project data and financial calculations.
5. A separate model invocation for structured financial output.
6. A Python validator that controls publication.

### User to Agent

User input is untrusted and must not override application
authorization or tool execution policies.

### Tools to Application

Tool results are treated as potentially untrusted.

Python validates expected structures and selected business
fields before accepting results.

### Application to Model

Financial data is validated before being passed to the model.

The model's output is not treated as authoritative.

### Model to User

Structured financial output must match the deterministic
Python reference before publication.

If validation fails, the response is blocked.

## 4. Threats and Implemented Mitigations

| ID | Threat | Mitigation |
|---|---|---|
| T01 | Prompt injection in tool data | Schema validation and trusted owner comparison |
| T02 | Unauthorized project access | Tool authorization rules |
| T03 | Excessive tool calls | Execution limits |
| T04 | Tool failure followed by fabricated output | Fail Closed behavior |
| T05 | Unexpected output fields | Allowlist validation |
| T06 | Sensitive information in explicit security logs | Allowlisted logging fields |
| T07 | Incorrect CPI or EAC generated by the model | Deterministic financial output guard |
| T08 | Inconsistent financial calculations from a tool | Recalculation using Python |
| T09 | Vulnerable dependencies | Dependabot alerts and updates |
| T10 | Accidental publication of supported secret types | GitHub secret scanning and push protection |

These mitigations are limited to the specific paths tested
in the laboratory.

## 5. Financial Output Validation

The financial validation experiment uses synthetic project P003.

### Input values

- BAC: 400000
- EV: 230000
- AC: 210000

### Calculation

CPI = EV / AC

EAC = BAC / CPI

Expected indicators:

- CPI: 1.0952
- EAC: 365217.39

EAC is calculated using the unrounded CPI.

The financial guard:

1. Validates the project identifier.
2. Validates financial inputs and the response schema.
3. Recalculates CPI and EAC.
4. Rejects invalid or unexpected values.
5. Checks structured model output against the Python reference.
6. Publishes a deterministic response only after validation.

## 7. Remaining Risks

### R01 — Authorization

Project permissions are simulated using Python configuration.

Production authorization requires authenticated identity,
trusted roles, and server-side access checks.

### R02 — Data Provenance

Financial recalculation proves mathematical consistency,
not that the original input values came from an authoritative source.

Production systems must verify data provenance and access rights.

### R03 — Prompt Injection

Schema checks and trusted-field comparison reduce specific risks.

Malicious instructions can still appear inside permitted text
fields and require additional defensive testing.

### R04 — Logs and Monitoring

The logging experiments cover selected explicit security events.

They do not constitute a complete audit of SDK logs,
tracing systems, platform logs, or exception handling.

### R05 — Limited Financial Scope

The financial output guard was tested for project P003.

Other projects, financial indicators, and unrestricted
natural-language responses are not automatically protected.

### R06 — Operational Security

The laboratory does not implement a comprehensive production
security program covering network restrictions, monitoring,
incident response, and credential lifecycle management.

### R07 — Availability and Cost

Execution limits reduce selected risks but do not replace
API rate limiting, timeouts, retry policies, monitoring,
or cloud spending controls.

## 8. Production Recommendations

Before production deployment:

1. Integrate real identity-based authorization.
2. Connect authoritative project data sources.
3. Extend validation to all supported business outputs.
4. Perform adversarial testing of prompts and tool results.
5. Audit credentials, logging, and tracing.
6. Add operational monitoring and incident response.
7. Review dependency updates and CI results.
8. Conduct an independent security assessment.

## 9. Conclusion

The laboratory demonstrates several complementary
AI agent security controls:

- Tool authorization
- Execution limits
- Schema validation
- Fail Closed behavior
- Allowlisted security logging
- Deterministic financial validation
- Dependency and secret protection

The central design principle is:

**Untrusted model output must not bypass deterministic
application security and business rules.**

These protections reduce specific risks but do not
eliminate all security threats.
